# SoundCollab

Україномовний статичний сайт SoundCollab / Xiao Entertainment для музичної індустрії та суміжних event-професіоналів. Тепер кабінети мають MVP-цикл замовлення на Supabase: email-авторизацію, профілі ролей, замовлення, приватний чат, зустрічі, здачу результату та журнал подій. GitHub Pages обслуговує лише HTML/CSS/JS; власного сервера немає.

Поточний короткий звіт про готовність, перевірки та наступні кроки: [`PROJECT_STATUS.md`](PROJECT_STATUS.md).

> **MVP, не платіжний сервіс.** Supabase працює лише після окремого налаштування проєкту. Оплата, ескроу, повернення коштів, власний відеозв’язок і зовнішні OAuth-інтеграції не реалізовані. Не надсилайте платіжні реквізити через чат.

## Функціональність

- `index.html`, `services.html`, `about.html`, `portfolio.html`, `faq.html` — публічний маркетинговий сайт, каталог та контентні напрямки Studio / Journal / Academy.
- `auth.html` — реєстрація з роллю клієнта, виконавця або обома ролями; обов’язкова згода з політикою конфіденційності; вхід, вихід, підтвердження email і відновлення пароля.
- `client.html` — створення запиту із послугою, назвою, описом, бюджетом, форматом (дистанційно / особисто), дедлайном і необов’язковим вибором виконавця; список статусів клієнта.
- `specialist.html` — профіль, місто, опис і посилання на портфоліо; вхідні відкриті або призначені запити; прийняття, відхилення та початок роботи.
- `order.html?id=<uuid>` — приватний робочий простір: покроковий індикатор прогресу, що відображає статус із БД і підказує наступну дію, чат, зовнішні Google Meet/Zoom/Microsoft Teams/Jitsi зустрічі, здача роботи посиланням/файлом, журнал подій, скасування й спір. Для відеозустрічі відкрий платформу, створи там зустріч і встав отримане invite-посилання; обидва учасники побачать кнопку приєднання. Це link-based підключення без OAuth/API-керування акаунтом провайдера. Індикатор не дозволяє пересувати статус напряму: переходи виконуються відповідними діями та повторно перевіряються в БД. Адміністратор із DB-прапорцем бачить перелік спорів у звичайному кабінеті та може переглядати відповідні замовлення, чат і журнал; окремої прихованої адмін-сторінки немає.
- `payments.html`, `rights.html`, `responsibility.html`, `privacy.html`, `terms.html`, `contact.html` — інформація й робочі чернетки політик. Юридичні тексти потрібно перевірити перед production.

## Запуск локально

```bash
python3 -m http.server 8000
# відкрийте http://localhost:8000
```

Supabase JS 2.117.3 постачається локально у `vendor/supabase-js-2.117.3.js`; офіційна npm-копія має контрольну суму в `vendor/SUPABASE-JS-SHA256.txt`, яку перевіряє CI. Сторінки кабінету не завантажують SDK з CDN. URL та публічний ключ уже задані в `supabase-config.js`, але Auth, таблиці, Storage та Realtime запрацюють лише після застосування схеми й налаштування проєкту. Якщо конфіг містить placeholders, кабінети покажуть попередження замість імітації успіху. Контактні форми зберігають наявний безпечний demo-fallback на `mailto:sound.collab.official@gmail.com`; телефон у HTML — demo placeholder.

## Налаштування Supabase

1. Створіть проєкт Supabase та дочекайтеся готовності Postgres.
2. У **SQL Editor** виконайте весь файл [`supabase/schema.sql`](supabase/schema.sql). Він створює таблиці, індекси, тригери, функції, RLS-політики, приватний bucket `order-files`, політики Storage та додає `messages` до `supabase_realtime`.
3. У **Project Settings → API** скопіюйте Project URL і лише публічний `anon` / publishable key у `supabase-config.js`:

   ```js
   window.SOUNDCOLLAB_SUPABASE_URL = "https://YOUR_PROJECT_ID.supabase.co";
   window.SOUNDCOLLAB_SUPABASE_ANON_KEY = "YOUR_PUBLIC_ANON_KEY";
   ```

   Ці значення призначені для браузера, але доступ до даних обмежують RLS-політики. **Ніколи не додавайте `service_role` key** у цей репозиторій, `app.js`, GitHub Pages чи браузерний код.

4. У **Authentication → URL Configuration** задайте Site URL для локальної розробки або production і дозвольте точні адреси callback, наприклад:

   - `http://localhost:8000/auth.html` and `http://localhost:8000/auth.html?view=update-password`
   - `https://<owner>.github.io/<repository>/auth.html` and `https://<owner>.github.io/<repository>/auth.html?view=update-password`

   Для production підставте реальні owner/repository. Налаштуйте email confirmation та recovery templates. Лише для disposable тестового проєкту можна тимчасово вимкнути Confirm email, але цей режим не перевіряє підтвердження пошти. Вбудований Supabase email має обмежену доставку/ліміти; для beta-тестерів підключіть власний SMTP.
5. Створіть користувачів через `auth.html`. Тригер створює `profiles` і фіксує `privacy_accepted_at` разом із версією політики. Щонайменше одну роль обрати обов’язково; ролі `client` і `performer` можуть співіснувати.
6. Щоб призначити окремий адміністраторський акаунт, після реєстрації цільового акаунта виконайте в SQL Editor (замінивши адресу на контрольовану вами). Не використовуйте один із двох acceptance-test акаунтів як адміністратора:

   ```sql
   update public.profiles p
   set is_admin = true
   from auth.users u
   where p.id = u.id
     and lower(u.email) = lower('admin@example.com');
   ```

   `is_admin` не можна призначити через клієнтський signup або зміну свого профілю. Адмінський прапорець і права перевіряються в БД; окремого прихованого адмін-інтерфейсу немає. Адмін бачить замовлення, повідомлення й файли лише поки замовлення має статус `disputed`.
7. Після конфігурації відкрийте `auth.html`, зареєструйтеся і перевірте реальну пошту. Перед production перевірте ліміти/типи файлів у Supabase Storage, SMTP, retention, резервні копії, privacy policy та юридичні умови.

### Якщо показано `Could not find the table 'public.profiles' in the schema cache`

Це означає, що для URL-проєкту в `supabase-config.js` ще не застосовано схему або PostgREST ще не оновив schema cache. Увійдіть у Supabase Dashboard саме проєкту `manyhvexvptcsfkfqmls`, відкрийте **SQL Editor**, виконайте весь актуальний `supabase/schema.sql` із репозиторію та дочекайтеся успішного завершення. Потім перезавантажте сайт. Схема ідемпотентна для її `create if not exists`/`create or replace` об’єктів; якщо SQL Editor повідомляє помилку транзакції, виправте її перед повторним запуском. Схема також створює профілі для раніше зареєстрованих користувачів, у чиїх Auth metadata збережено `privacy_consent: true`.

Якщо після успішного SQL запуску таблиця все ще не знаходиться, виконайте окремо `NOTIFY pgrst, 'reload schema';` у SQL Editor або зачекайте хвилину, і перевірте, що URL у конфігурації збігається з відкритим проєктом. Не надсилайте пароль чи ключі підтримці.

`Invalid login credentials` — окрема помилка авторизації: перевірте email/пароль або скористайтеся «Забули пароль?». Відсутня `profiles` не виправляється повторним введенням пароля; спершу застосуйте SQL-схему.

### Застосування патчу до вже налаштованої схеми

Для тестового проєкту, де попередня версія `schema.sql` вже застосована, запускайте [`supabase/migrations/20261015_schema_review_fixes.sql`](supabase/migrations/20261015_schema_review_fixes.sql) один раз у Supabase SQL Editor. Файл використовує транзакцію і в разі помилки має відкотити зміни; перед запуском зробіть backup та перевірте наявні self-assignment/duplicate open dispute рядки, які блокують constraints. Для нового проєкту достатньо актуальної `schema.sql`; migration вдруге не запускати.

Для проєкту, де схема вже розгорнута і потрібно окремо закрити прямий REST-доступ до trigger-функцій, перегляньте [`supabase/db-harden-live.sql`](supabase/db-harden-live.sql) та виконайте його вручну в SQL Editor. Цей live SQL не запускається автоматично в CI і не був застосований до віддаленого проєкту. Він також відкликає виконання helper-функції `public.rls_auto_enable()`, якщо вона присутня в цільовому проєкті; якщо її там немає, цей рядок дасть помилку й потрібно виконати решту рядків без нього.

`supabase-config.js` містить Project URL і public publishable/anon key, а не секрет. Будь-який відвідувач може прочитати браузерний код і цей ключ; безпека залежить від коректних SQL-політик і налаштувань Supabase. Supabase JS закріплений на версії `2.117.3`; ліцензія включена в `vendor/SUPABASE-JS-LICENSE.txt`.

## Схема та контроль доступу

- `profiles`: один рядок на користувача Auth; ролі `client`/`performer`, портфоліо та `is_admin`. Публічно автентифікованим користувачам показуються лише профілі виконавців і дозволені поля; приватні профілі доступні власнику та учасникам спільних замовлень. `is_admin` і timestamps згоди не видаються через API. DB-тригер забороняє самопризначення адміністратора і зміни запису згоди.
- `orders`: бюджет зафіксовано у гривні (`UAH`); акаунт клієнта не можна призначити виконавцем того самого замовлення. Створення починається як `draft`; клієнт може редагувати чернетку до надсилання. Після цього UI викликає DB RPC `transition_order`. Статус і дозволені актори перевіряються тригером, а RLS приховує чернетки від виконавців.
- Переходи: `draft → requested → accepted | declined → in_progress → delivered → completed`; дозволені також `cancelled` та `disputed` згідно з роллю та попереднім статусом. Непризначений виконавець може прийняти відкриту заявку, але не може відхилити її для всіх; відхиляти можна лише персонально призначений запит. Для `delivered` у БД має вже існувати файл або посилання на результат. `disputed` вимагає причини; невідповідні зміни відхиляються базою.
- `messages`: читання та створення доступні лише клієнту, призначеному виконавцю й адміну; немає UPDATE/DELETE grants. Realtime передає нові повідомлення з цими ж RLS-обмеженнями. Користувацький текст виводиться екранованим.
- `meetings`: створення/відповідь — через DB-функції; інша сторона підтверджує, відхиляє або пропонує інший час. Перенесена зустріч повертається в `proposed` із новим автором пропозиції, тому інша сторона може підтвердити новий час. Для Google Meet, Zoom та Microsoft Teams UI відкриває вебсайт сервісу для створення зустрічі; користувач вставляє invite URL, а учасники приєднуються за кнопкою у замовленні. Зустріч іде під акаунтом власника у зовнішньому сервісі. Немає OAuth/API інтеграції, створення зустрічі від імені SoundCollab, синхронізації календаря чи автоматичного видалення посилань. Jitsi-кнопка формує випадкове зовнішнє посилання; це не власний відеосервіс. Адміністратор не є учасником зустрічі. Також доступні адреса/карта для зустрічі наживо. Для першої зустрічі наживо рекомендується публічне місце.
- `order_events`: журнал статусів, пропозицій зустрічей та спорів із часом і автором; клієнтські INSERT/UPDATE/DELETE заборонені, записи додають DB-тригери.
- `order_disputes`: причини/рішення спорів доступні учасникам, а адміністратору — лише під час відкритого спору. `resolve_order_dispute` фіксує автора, результат, пояснення, час і подію в журналі; звичайна зміна статусу не замінює цього рішення.
- Адміністратор не має загального доступу до замовлень, чатів і файлів. RLS дозволяє адмін-перегляд лише для замовлень зі статусом `disputed`; адмінська дія дозволена тільки через RPC вирішення спору і потрапляє в журнал.
- `order_deliverables` і приватний Storage bucket `order-files`: доступ до замовлення перевіряється RLS; файли відкриваються короткостроковими signed URLs. Ліміт сховища — 50 MiB на файл; для аудіоархівів рекомендується приватне зовнішнє посилання.

## GitHub Pages

`.github/workflows/pages.yml` публікує статичні файли з `main` через GitHub Actions. У **Settings → Pages** використовуйте GitHub Actions. Supabase URL і anon key можна зберігати в tracked `supabase-config.js`, але service key — ні. Після зміни Auth redirect allowlist перевірте email callback на production URL. GitHub Pages не виконує серверний код і не приховує браузерні значення.

`.github/workflows/db-tests.yml` на кожен pull request запускає `supabase/tests/test_rls.py` проти чистого PostgreSQL 17, застосовуючи тестовий mock platform і `supabase/schema.sql`. Сценарій перевіряє RLS, переходи статусів, ролі, повідомлення, зустрічі, deliverables, арбітраж, Storage і права DB-функцій; mock призначений лише для CI й тестів, не застосовуйте його до реального Supabase-проєкту. Локальний запуск потребує PostgreSQL та `psycopg2-binary==2.9.10`:

```bash
export PGHOST=localhost PGUSER=postgres PGPASSWORD=postgres PGDATABASE=sc_test SC_APPLY_SCHEMA=1
python3 -m pip install psycopg2-binary==2.9.10
python3 supabase/tests/test_rls.py
```

Тест застосовує схему лише коли задано `SC_APPLY_SCHEMA`; база має бути чистою. `schema.sql` більше не створює `pgcrypto`: CI використовує PostgreSQL 17, де `gen_random_uuid()` є вбудованою функцією.

## Ручний acceptance test

Тестуйте на налаштованому Supabase-проєкті у двох окремих браузерах/профілях (або звичайному та приватному вікні) з підтвердженими акаунтами:

1. У браузері A створіть акаунт клієнта з обов’язковою згодою, підтвердіть email і увійдіть. У браузері B створіть акаунт виконавця, підтвердіть email, заповніть профіль та портфоліо.
2. Як клієнт створіть remote або in-person замовлення, виберіть виконавця B (або залиште відкритим) і перевірте появу `requested` у кабінеті.
3. Як виконавець прийміть запит, відкрийте те саме замовлення, змініть статус на `in_progress`. Надішліть повідомлення з браузера A і переконайтеся, що воно з’являється через Realtime у B. Спробуйте відкрити URL замовлення з неавторизованого третього браузера — доступ має бути відхилено.
   Перевірте, що покроковий прогрес оновлюється разом зі статусом, показує наступний крок для поточної ролі й не змінює статус при натисканні на етапи індикатора.
4. Для Google Meet, Zoom або Microsoft Teams натисніть кнопку відкриття платформи, створіть там зустріч у власному акаунті, вставте invite URL, надішліть пропозицію та перевірте кнопку «Приєднатися» в обох учасників. Окремо перевірте випадкове Jitsi-посилання. Перенесіть час з другого акаунта, переконайтеся, що пропозицію бачить перша сторона й вона може підтвердити новий час. Для in-person перевірте місце/карту та підказку про публічне місце.
5. Як виконавець передайте URL або невеликий файл до 50 MiB. Переконайтеся, що без результату БД не дозволяє перейти в `delivered`, а файл приватний і доступний через короткострокову signed URL; відкрийте результат як клієнт і завершіть замовлення.
6. Створіть друге тестове замовлення, дійдіть до `accepted` або `in_progress` і відкрийте спір із причиною з одного акаунта. У третьому браузері увійдіть адміністратором, призначеним SQL-командою вище: спір має бути видимим у звичайному кабінеті, а сторінка спору — показувати чат і журнал. Зафіксуйте рішення поясненням; перевірте status/event/dispute audit. Перевірте, що адміністратор не може бачити завершені/звичайні замовлення або їх чат/файли.
7. Перевірте вихід, повторний вхід, запит на скидання пароля та пароль із recovery-посилання. Перевірте, що учасник не може редагувати/видаляти повідомлення, підробляти події, змінювати чужі замовлення чи самостійно призначити `is_admin`; профілі клієнтів і внутрішні поля профілів не читаються стороннім акаунтом.

Для повного тесту потрібні реальна поштова скринька, два користувачі/браузери та окремий адміністратор для незалежної перевірки спору. У репозиторії є лише публічний Project URL і publishable key; секретів немає. Acceptance test потрібно запускати лише після того, як описану схему буде застосовано до потрібного Supabase-проєкту.

## Межі MVP та довіра

- Реєстрація та робочий процес запитують Supabase напряму з браузера; GitHub Pages не має власного сервера. Не зберігайте в акаунті або чаті дані картки, приватні ключі, паролі сторонніх сервісів чи чутливі персональні дані.
- Реальних платежів, 10% утримання/списання, ескроу, виплат, повернення та рахунків ще немає. 10% — запланована бізнес-модель і має бути реалізована лише через узгоджений PSP/серверну бухгалтерську логіку.
- Відео використовує зовнішні invite-посилання. Створення через API, OAuth Google/Zoom/Teams, автоматична перевірка чинності invite-посилань і запис дзвінків відсутні.
- Поштові сповіщення поки обмежені Auth-підтвердженням і recovery; немає окремих order email/in-app notification, календарної синхронізації, антивірусної перевірки, історії версій файлів чи гарантії зберігання.
- Самостійне видалення акаунта/експорт даних і захист від масових signup/order/message submissions ще не реалізовані; потрібні окремий підтверджений процес і anti-abuse обмеження до бета-запуску.
- Базове DB-обмеження приймає не більше 5 нових замовлень від клієнта за 10 хвилин і 30 повідомлень від користувача за хвилину; це лише стримування спаму, не повноцінна антибот/anti-abuse система.
