# SoundCollab — стан проєкту

**Оновлено:** 15 жовтня 2026

**Поточний реліз:** MVP у відкритому [PR #2](https://github.com/raduydar-afk/soundcollab/pull/2)
**Висновок:** фронтенд і схема MVP реалізовані, CI для бази та статичного сайту проходить. Повний реальний сценарій замовлення ще заблокований: Supabase API проєкту, вказаного у браузерній конфігурації, повертає `PGRST205` — таблиця `public.profiles` відсутня у schema cache. Потрібно застосувати актуальну схему в Supabase Dashboard і повторити тест.

## Що вже готово

- Україномовний адаптивний сайт SoundCollab з каталогом послуг, портфоліо, контентними розділами та GitHub Pages workflow.
- Сторінка акаунта: signup з ролями client/performer, обов’язкова згода з політикою, входження, вихід, підтвердження email і recovery-потік.
- Кабінети клієнта та виконавця, створення запиту/замовлення, профіль виконавця, прийняття/відхилення та передача результату.
- Робочий простір замовлення з учасницьким чатом через Supabase Realtime, зустрічами, приватними файлами/посиланнями, статусами, журналом та подачею спору.
- `supabase/schema.sql`: таблиці, RLS, DB-перевірки ролей і переходів, приватний Storage bucket, audit-журнал, функція рішення спору й backfill профілів для раніше зареєстрованих користувачів із зафіксованою згодою.
- Окрема транзакційна schema-review міграція для проєктів, де застосовувалася попередня схема.
- Автоматичні PostgreSQL 17/RLS тести на основі тестового mock та перевірки JavaScript/HTML у GitHub Actions.
- Supabase JS **2.117.3** закріплено та включено локально, без CDN-завантаження бібліотеки.
- Офіційна npm-копія SDK перевіряється CI за SHA-256 manifest; пряме виконання trigger-функцій відкликане у schema.
- Конфігурація браузера використовує лише публічний Supabase publishable key; секретний `service_role` key у код не додавався.
- Застарілий `gemini-code-1789771324934.html` видалений.

## Що перевірено

- DB/RLS CI suite пройшов на чистому PostgreSQL 17.
- Static-site CI пройшов, включно з JavaScript syntax та локальними HTML-посиланнями.
- Локальні перевірки SQL parse, JavaScript parse, HTML links і `git diff --check` пройшли.
- Браузерний preview завантажує локальний SDK і головну сторінку.
- Віддалений Supabase REST endpoint перевірено: запит до `public.profiles` повертає `PGRST205` / `Could not find the table 'public.profiles' in the schema cache`.

CI перевіряє схему на тестовому PostgreSQL із mock-об’єктами Supabase. Це **не підтверджує**, що схема вже застосована до реального Supabase-проєкту або що реальна пошта/Realtime/Storage налаштовані.

## Що ще треба зробити — у правильній послідовності

1. **Застосувати схему в Supabase.** Увійти в Dashboard потрібного проєкту, відкрити SQL Editor, виконати актуальний `supabase/schema.sql` із PR #2 і переконатися, що транзакція завершилася без помилки. Не виконувати mock SQL у реальному проєкті.
2. Якщо API далі не бачить таблиці — виконати `NOTIFY pgrst, 'reload schema';`, перевірити URL проєкту в `supabase-config.js` та зачекати оновлення schema cache.
3. Перезавантажити сайт і перевірити реєстрацію/вхід. `Invalid login credentials` — окрема помилка: потрібні правильні дані наявного акаунта або password recovery; таблиця не створює й не виправляє пароль.
4. Налаштувати Supabase Auth Site URL, точні redirect URLs, email confirmation/recovery templates і, для зовнішніх тестувальників, SMTP.
5. Створити два різні тестові акаунти (клієнт і виконавець) і окремий третій адмінський акаунт. Пройти ручний acceptance-сценарій із README: замовлення → прийняття → чат → зустріч → результат → завершення та окремий спір із рішенням адміністратора.
6. Перед реальними користувачами перевірити RLS/Security Advisor у самому Supabase-проєкті, ліміти Storage, backup/restore, privacy retention і юридичні тексти.

## Обмеження — функціональність ще не заявляється як production

- Реальні платежі, ескроу, виплати, повернення і нарахування 10% комісії відсутні. Вказані 10% — затверджена бізнес-модель на майбутнє, не активний платіж.
- Завантаження обмежене 50 MiB на файл; великі аудіо треба передавати приватним посиланням.
- Адміністратор має DB-прапорець і доступ до замовлення/чату/файлів лише поки спір відкритий; рішення записується через DB RPC та журнал.
- Зустрічі використовують зовнішні Jitsi/Zoom/Meet/Teams URL; власного відеозв’язку та OAuth-інтеграцій немає.
- Немає окремих order email/push notifications, календарної синхронізації, антивірусної перевірки, версій файлів, self-service account deletion/export чи повної anti-abuse системи.
- Privacy/terms/rights/responsibility — робочі чернетки, які потрібно юридично перевірити до production.

## Локальний перегляд

```bash
python3 -m http.server 8000
```

Потім відкрийте `http://localhost:8000/`. Без застосованої схеми та налаштувань Supabase UI завантажується, але автентифіковані сценарії не пройдуть. Інструкції з Supabase й ручний тест: [`README.md`](README.md). Подальший продуктовий план: [`ROADMAP.md`](ROADMAP.md).
